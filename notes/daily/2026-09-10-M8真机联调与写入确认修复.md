# 2026-09-10（第三轮，首次真实 PLC 联调）

## 今日目标

- 在真实 S7-1200 上把 `DB_M8_Acceptance` 通信与 FIFO/出队/LED 语义跑通。
- 定位真机自动验收随机失败的原因，并给出可复现的修复。

## 今日环境

- 电脑：Windows 11（当前开发机）；Python 3.12.10（`.venv`）；python-snap7 3.1.2
- 对照环境：`%TEMP%\s7check`（原生 python-snap7 1.3）
- Git commit：`b3061d3`（运行基线；本轮改动未提交）
- 摄像头：未使用
- PLC：S7-1200 CPU 1214C DC/DC/DC `6ES7 214-1AG40-0XB0`，固件 4.5.1，`192.0.2.1`

## 今天做了什么

1. 确认 TIA 中"允许来自远程对象的 PUT/GET 通信访问"与"完全访问权限"生效后，PC 侧 DB 读写打通（`--diagnose` 的 `db_read_ok=true`、`hint=[]`）。
2. 只读量出 DB3 恰为 24 字节，确认就是 `DB_M8_Acceptance`；OB1 改为路径 B 后 `--check-access` 通过（`magic=0x4D38`、`CycleCounter` 递增）。
3. `--all` 首次随机失败；用"手动逐拍时序 + 独立连接旁观 + M 区对照 + 原生库对照"定位到：**PUT/GET 写 `DB_M8_Acceptance`（程序每扫描访问的 DB）控制字会被静默丢弃约一半**，M 区写则 10/10 可靠。
4. 给验收工具与 PC 侧桥加"写→读回→重发"，重跑 `--all` **12/12 AUTO PASS**；全量 pytest 196 passed。
5. 顺手纠正：仓库锁定的 `python-snap7 3.1.2` 是纯 Python 重实现，`get_cpu_state()` 是占位实现，曾被它误导；已从 `--diagnose` 移除该探针。原生库读到在线固件 **4.5.1**。

## 结论与影响

- M8 真机链路（PC ↔ PLC ↔ FIFO ↔ 出队 ↔ LED 状态）在 DB 语义层已打通。
- **M7 的共享协议必须包含写入确认/ACK**，"写一次即送达"在这台 CPU 上不成立。
- 实体 LED、物理按键、断电重启、视觉接入仍是待补证据，M7/M8/M9 不因此置为 DONE。
