# 项目负责人和 PLC 同学协作约定

生效：2026-09-05，依据负责人本次委派。项目由仓库所有者主导，同学承担 PLC 部分。

## 责任与修改边界

| 范围 | 负责方 | 协作规则 |
|---|---|---|
| 需求、架构、路线图、证据总表、根 AGENTS、依赖与仓库设置 | 项目负责人 | 同学提交建议，由负责人定版 |
| `pc/`、`simulator/`、PC 测试及运行配置 | 项目负责人 | PLC 同学不得为配合自身实现直接修改 |
| `plc/` 下程序、工程归档、变量表、I/O、内部设计与本地测试记录 | PLC 同学 | 专属分支开发；读取 `plc/AGENTS.md` |
| `docs/PLC_INTERFACE.md` 共享契约、形状编码、ACK、心跳、重发 | 负责人定版，双方评审 | 同学在 `plc/docs/` 提提案；不得单方面改双方接口 |
| 真实联调、最终验收、合并主分支 | 项目负责人统筹 | 同学提供 PLC 证据，负责人审计并更新里程碑 |

同学可以开始硬件核实、PLC 内部设计及不依赖未定接口的独立开发；涉及帧解析、通信块、端口、DB 布局等时，先提交接口提案。本次文档更新不代表已开始 M6–M10 功能开发，也不豁免其验收前置条件。

## 克隆后的工作流程

1. 在仓库根目录启动 Codex，先读根 `AGENTS.md`、`docs/PROJECT_SPEC.md`、本页、`docs/PLC_HARDWARE.md`、`docs/PLC_INTERFACE.md`、`plc/AGENTS.md`。PLC 工作无需安装 PC 的 Python/GUI 环境。
2. 先 `git status --short` 和 `git fetch origin`，检查实际默认分支及负责人已合并的版本。当前主分支为 `master`；工作区非空时先保留自身修改，不强制覆盖。
3. 从最新 `origin/master` 新建独立分支，例如 `git switch -c codex/plc-io-survey origin/master`。每个分支只做一件事，先声明目标、Requirement ID、修改路径、接口依赖和验证方式。
4. 只提交自己的明确路径（例如 `git add plc/`，并复核 staged diff），使用说明清楚的小提交。保存 TIA 工程前关闭相关编辑，避免复制正在写入的数据库。不要在两台电脑同时改同一 TIA 工程归档。
5. 推送自己的分支并在 GitHub 提交 PR 给负责人审阅；PR 写明改动、接口版本、TIA/CPU 环境、已执行测试、待测试项与证据路径。PLC 同学及其 Codex 不自行 merge，也不向 `master` 直接 push。
6. 合并前同步主分支；文本冲突逐项处理，TIA 二进制冲突不得用 ours/theirs 猜测解决，应由 PLC 同学基于最新工程重做并重新编译验证。负责人确认后合并。

不得 force push、重写共享历史、修改远端权限/分支保护，或把 Collaborator 身份视为扩大任务范围的授权。Codex 不应自动发送消息或创建对外 PR，除非其当前操作者已明确授权该动作。

## 可审阅的 PLC 交付

- `plc/src/`：可导出的 SCL/XML 等文本源码；使用 LAD/FBD 时提供变量表与可阅读的网络图/PDF，不能仅有截图。
- `plc/project/`：可恢复的 TIA 项目归档及恢复说明；稳定版本保留一份，清晰写明 TIA 版本、CPU 订货号/固件、源代码 commit、归档 SHA-256 与生成步骤。大文件走负责人确定的存放方案，不上传虚拟机镜像。
- `plc/docs/`：I/O 表、内部设计、接口提案、环境记录；`plc/tests/`：测试步骤与预期；`plc/records/`：日期+主题命名的实验/测试/问题记录，避免争用根目录连续编号。
- PLC 局部证据可放 `plc/evidence/` 精选小文件。负责人在审核时将索引汇入 `notes/daily/`、`notes/tests/`、必要的 `notes/issues/` 和 `docs/REPORT_EVIDENCE.md`。
- 每条测试写 Git commit、环境、输入、步骤、预期、实际和证据。明确区分未执行、编译、PLCSIM 模拟、真实 PLC 测试；模拟通过不标真实 PASS。

最低测试范围：FIFO 容量 ≥3、顺序/满/空、按键一次只出队一个、复位清空、三种 LED 数量；后续接口冻结后补心跳 1 s、断连 2 s 全闪、重发不重复入队、队列满反馈与恢复。没有执行的项目保持“待测试”。
